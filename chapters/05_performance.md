# 第5章 遅い SQL を速くする（目安 23 分・うち講師デモ 5 分）
## この章でやること
クエリプロファイルで「読んだデータ量」「読んだパーティション数」「結合後の行数」を見て、書き換えで速くなることを体験します。
## 前提
第0章が終わっていること。約6,000万行の明細表（LINEITEM_SORTED）を使います。
## 手順
新しい SQL ファイル（Projects → Workspaces →「SQL file」）に [sql/05_performance.sql](../sql/05_performance.sql) を貼り付け、1文ずつ実行します。各 SQL の実行後、画面下の「Query History」で該当する行の右端にあるクエリ ID を押し、開いた画面の「Query Profile」タブで右側の「Statistics」を見て、下の表に記録します（Monitoring → Query History からも開けます）。
| パターン | 見る指標 | 改善前 | 改善後 |
|---|---|---|---|
| P1 SELECT * | スキャン量 | | |
| P2 関数で加工した絞り込み | パーティション数 | | |
| P3 結合キー不足 | 結合後の行数 | | |

続けて P4（ウェアハウスのサイズ変更）と P5（結果キャッシュ）も実行します。P4 では、サンプルデータの大きい表（TPCH_SF100・明細 約6億行）を使う同じ重い集計を、X-Small から X-Large まで5段階のサイズで実行し、秒数を記録します（秒数は画面下の結果の右上に出ます）。サイズを上げると最低1分ぶんの料金がかかりますが、5段階すべてで約0.5クレジットで、トライアルの無料枠には十分収まります。

| サイズ | 1時間あたりのクレジット | 秒数 |
|---|---|---|
| X-Small | 1 | |
| Small | 2 | |
| Medium | 4 | |
| Large | 8 | |
| X-Large | 16 | |

**P4 の最後に、必ずサイズを X-Small に戻し、`SHOW WAREHOUSES` の size 列が X-Small になっていることを確かめてください。**
## 確認ポイント（期待結果）
- P1: スキャン量が改善後に減ります（例: 約 6.3MB → 約 1.1MB）
- P2: 件数はどちらも 774,721。パーティション数が改善後に大きく減ります（例: 49 → 2）
- P3: 改善前 3,098,884 行 → 改善後 774,721 行
- P4: サイズを上げるほど秒数が短くなります。料金は「1時間あたりのクレジット × 動いた時間」なので、倍のサイズで半分の時間なら費用はほぼ同じです（講師アカウントでの例: X-Small 約5〜9秒 → X-Large 約1〜2秒。同じ SQL の2回目は、読み込んだデータが手元に残るため速くなります）

## うまくいかない時
- 2回目以降すぐ終わる: 結果キャッシュが効いています。最初の `ALTER SESSION SET USE_CACHED_RESULT = FALSE;` を実行してください。
- P4 の後は必ずサイズを XSMALL に戻してください（`SHOW WAREHOUSES LIKE 'HANDSON_WH';` で確認）。
- サイズを変えた直後の1回目は、ウェアハウスの準備で数秒かかることがあります。
